# Writing a plugin

A plugin adds a mark, a block or an inline element to the editor. A mark styles a run of text, such as bold. A block is a paragraph-sized unit, such as a quote. An inline is a small element inside a line of text, such as a mention.

Every example on this page is real code. Each excerpt is read from the file named in the line above it, except the one sketch that says it is not.

## A mark in one file

A feature has two parts. The content (`defineContent`) says what a document can hold and how each node is written as HTML and read back. The plugin (`definePlugin`) adds the editing on top: toolbar buttons, keys and typing rules.

Keep them apart because the renderer reads only the content. A page that shows documents keeps the content and drops the plugin with its editing code. Mark the `definePlugin` call `/* @__PURE__ */` so the bundler can drop it.

The button asks the editor instead of working things out itself: `isActive` says whether the selection has the mark, and `toggle` turns it on or off. `shortcut` binds the key to the same toggle.

`definePlugin` takes its `id` from the only type the content declares. With several types, give it an `id`.

`toolbarButtonClasses` is the story's own styling. Use your own classes in its place.

Pass the plugin to the editor and the content to the renderer.

```tsx
<RichTextEditor plugins={[...defaultPlugins, acmeHighlightPlugin]} value={doc} onChange={setDoc} />
<RichTextRenderer plugins={[...defaultContent, acmeHighlightContent]} value={doc} />
```

## Toolbar entries and hotkeys

A plugin lists its toolbar controls in `toolbar`. Each entry is data:

- `label` is required. It is the button's accessible name, its tooltip and, when the entry sets `menu`, its name in the `/` menu.
- `icon` is the button's icon, a component such as one from `@frontify/fondue-icons`.
- `shortcut` is a key in `Mod-b` style. The tooltip shows it, and it toggles the entry's type.
- `toggles` names the mark, block or inline the entry turns on and off. It defaults to the only type the content declares.
- `render` draws custom UI in place of the button. It gets the entry's `label` to name it with, `isActive` (`true`, `false` or `'mixed'` when only part of the selection has the mark) and a `toggle` function that turns the entry's type on or off. It also gets the `api`, the `selection`, the `selectedNode` and `openEditor`. An entry has an `icon` or a `render`.

`toolbarGroup`, on the plugin, picks the toolbar cluster its entries sit in. It is `{ id, order }`: groups are drawn by `order`, lowest first, and plugins that share an `id` give it the same `order`. The built-in groups are exported as `TOOLBAR_GROUPS`, 100 apart so a host can place its own between two of them. A plugin without a group sits after every group.

Source: `src/plugins/Underline/Underline.ts`

<Source code={underlinePluginExcerpt} language="ts" />

To put a host group between two built-in ones, give it an `order` between theirs:

```ts
const reviewPlugin = definePlugin({
    content: reviewContent,
    toolbarGroup: { id: 'review', order: TOOLBAR_GROUPS.link.order + 10 },
    toolbar: [{ label: 'Review', render: ReviewButton }],
});
```

For a key that does something other than toggle the entry's type, use `hotkeys`. Each binding needs a `label` and a `run` function. `Mod` is Cmd on macOS and Ctrl elsewhere. Avoid keys the system or browser takes, such as `Mod-h`, which hides the app on macOS.

The label is not optional. The [Keyboard reference](?path=/docs/rich-text-editor-guides-keyboard-reference--docs) page is written from these labels and the toolbar shortcuts, so a plugin that gains a key appears there with no edit to that page.

## Parse rules and HTML output

Every definition says how it is written and how it is read back.

- `toHtml` takes the node's value and returns an `HtmlSpec`: a `tag`, optional `attrs` and `children`. `children: true` is where the node's content goes. A string is fixed content.
- `parse` is a list of rules that read pasted HTML back into the node. A rule has a `tag`, a CSS selector such as `a[href]`. Its optional `value` function reads the value from the element, or returns `null` when the element is not this node after all.

A mark that is only a tag can skip both with `defineMark({ tag: 'u' })`. A mark also takes parse rules for inline styles, as Google Docs writes them. A `style` rule matches an element that declares that CSS property, and its `value` function gets the declared value.

A sketch of both rules on one mark, not code from the package:

```ts
const declaresUnderline = (cssValue: string): Record<string, never> | null => {
    if (cssValue.includes('underline')) {
        return {};
    }
    return null;
};

defineMark({
    tag: 'u',
    parse: [{ tag: 'u' }, { style: 'text-decoration', value: declaresUnderline }],
});
```

## Naming your types

Prefix the type names you store with your own namespace: `acme-callout`, `acme-highlight`, `acme-embed`. A stored type is part of your documents for good. The package may ship a `callout` or a `highlight` later, and an unprefixed type would then clash with it.

Every `acme-` example above follows this rule. The prefix is in the stored type and the mark key. The toolbar `label` is what people read, so it stays plain.
