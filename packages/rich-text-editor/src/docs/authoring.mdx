# Feature authoring

A feature has up to three parts. The vocabulary part says what a feature stores and how that content becomes HTML, Markdown and text. The editor part says what the editor does with it: commands, keys, input rules, toolbar entries, overlays, panels, decorations, suggestion lists, node views and file drops. The reader part renders a node or mark with your own component. A plugin is the whole plugin: the feature, its editor part and its reader part, which a host lists once.

The reader, the codecs and a server load only the vocabulary part. They never load editor code. Keep a feature's vocabulary in its own module, and import editor code only in the module that calls `defineEditorPart`.

Every example on this page is an excerpt of a shipped feature or of an example module under `src/docs/authoring`, and the `Source` line names its file. A test checks that each excerpt is still in that file. The `Rich Text Editor/Authoring` stories mount four of them as a host does: the `marks.strike` plugin, the one-file highlight mark, a host block with a node view, and a host plugin that replaces a shipped toolbar entry.

## Your first plugin: a mark in one file

This is a whole plugin, a highlight mark, in one file. It declares the mark, binds a key, adds one input rule and one toolbar toggle, and builds the plugin. It imports `defineFeature` from `@frontify/fondue-rich-text-editor/model` and the other three names from `@frontify/fondue-rich-text-editor/authoring`.

Source: `src/docs/authoring/highlight.ts`

```ts
/** A host mark, stored as `highlight`: `<mark>` in HTML and `==text==` in Markdown. */
const highlight = defineFeature({
    id: 'acme.highlight',
    version: 1,
    requires: [{ id: 'core', version: 1 }],
    marks: {
        highlight: {
            attrs: {},
            html: ['mark', 0],
            parse: [{ tag: 'mark' }],
            markdown: { open: '==', close: '==' },
        },
    },
    formats: { html: 'lossless', text: 'lossy', markdown: 'lossless' },
});

/** The whole plugin: a key, a typed `==text==` and a toolbar toggle, one file because no server reads it. */
export const highlightPlugin = definePlugin({
    feature: highlight,
    editor: defineEditorPart(
        highlight,
        toggleMark({
            mark: 'highlight',
            keys: ['Mod-Shift-h'],
            inputRules: [{ id: 'highlight.equals', open: '==', close: '==' }],
            toolbar: { labelKey: 'RichTextEditor_highlight', icon: 'IconPen' },
        }),
    ),
});
```

A host adds it to the list it gives `defineEditor`, as in `plugins: [corePlugin(), highlightPlugin()]`, and passes the same list to `modelOf`. The toolbar entry names a string key, `RichTextEditor_highlight`. A host plugin cannot add to the package strings, so the host's `locale` prop holds that key: the `enUS` strings plus `RichTextEditor_highlight: 'Highlight'`. This is all a toggle mark needs. The sections below cover the rest, when a plugin needs it: nodes, attributes, overlays, readers and migrations.

## A feature folder

A custom feature is a folder, as each shipped feature is. It holds these files:

- `feature.ts`: the vocabulary part, one `defineFeature` call. Its factory is what the file exports.
- `editor.ts`: the editor part, one `defineEditorPart` call for that feature.
- `reader.tsx`, optional: the renderers of the feature's nodes and marks. Add it only when the feature needs your own components to read.
- `index.ts`: `definePlugin({ feature, editor, reader? })`, which builds the plugin. A host lists this plugin and nothing else of the folder.

A shipped feature keeps three files, `feature.ts` (server-safe), `editor.ts` and `index.ts`, because server code imports its vocabulary without editor code. A host plugin that no server reads can keep everything in one file, as the callout does.

The folder keeps the vocabulary apart from the editor code, so the reader, the codecs and a server import `feature.ts` and never `editor.ts`. A shipped feature with a reader passes it too, as `definePlugin({ feature: link, editor: linksEditor, reader: linkReader })` does in `src/plugins/Link/index.ts`.

## The vocabulary part: `defineFeature`

`defineFeature` comes from `@frontify/fondue-rich-text-editor/model`. It returns a factory. Call the factory, even with no options, and pass the result to `compileContentModel` with `core()` and every feature it requires.

```ts
import { core, strikethrough } from '@frontify/fondue-rich-text-editor/features';
import { compileContentModel, defineFeature } from '@frontify/fondue-rich-text-editor/model';

const model = compileContentModel([core(), strikethrough()], { id: 'acme.notes', version: 1 });
```

A feature declares:

- `id` and `version`. A document records both in `requiredCapabilities`. Raise `version` when the stored shape of the feature's content changes.
- `requires`: the capabilities that must be installed at exactly these versions. A feature that builds on the document and the paragraph requires `core`.
- `nodes`, `marks`, `attributes`, `options`, `formats` and `parseRules`, as the examples below show.
- `codecs` and `migrations`. No shipped feature uses them yet, so this page has no excerpt for them. Their types are `CodecOverrides` and `CapabilityMigration`.

### Nodes

A node names its group, its content, its attributes, how it becomes HTML (`html`) and which HTML becomes it (`parse`). `formats` says whether each output is `lossless` or `lossy`, so a codec can report what it drops. A feature also declares its content check rules in `contentRules`. The excerpt stops before them, and `LEVELS` is `[1, 2, 3, 4, 5, 6]`.

Source: `src/plugins/Heading/feature.ts`

```ts
/** Headings `h1` to `h6`, whose level only the `level` attribute sets. */
export const heading = defineFeature({
    id: 'blocks.heading',
    version: 1,
    requires: [{ id: 'core', version: 1 }],
    nodes: {
        heading: {
            group: 'block',
            content: 'inline*',
            attrs: {
                nodeId: { type: 'string', required: true },
                level: { type: 'integer', min: 1, max: 6, required: true },
                lang: { type: 'language', nullable: true, default: null },
            },
            html: [
                { attr: 'level', tags: { 1: 'h1', 2: 'h2', 3: 'h3', 4: 'h4', 5: 'h5', 6: 'h6' } },
                { lang: { attr: 'lang' } },
                0,
            ],
            parse: LEVELS.map((level) => ({
                tag: `h${level}`,
                attrs: { level: { value: level }, lang: { from: 'lang' } },
            })),
        },
    },
    formats: { html: 'lossless', text: 'lossy', markdown: 'lossless' },
```

### Marks and options

A mark has attributes, an HTML spec and parse rules. `inclusive: false` keeps text typed at the end of the mark outside it. An option is serializable data with a default. A host passes it to the factory, as in `language({ languages: ['en', 'de'] })`, and the editor part reads it from the compiled model.

Source: `src/plugins/Language/feature.ts`

```ts
const DIRECTIONS = ['ltr', 'rtl', 'auto'] as const;

/** A passage's language and direction; text typed at a passage's end stays outside it. */
export const language = defineFeature({
    id: 'marks.language',
    version: 1,
    requires: [{ id: 'core', version: 1 }],
    options: {
        /**
         * The language tags the editor offers as choices; with none, the author types a tag.
         *
         * @default []
         */
        languages: { type: 'list', items: { type: 'language' }, default: [] },
    },
    marks: {
        language: {
            attrs: {
                lang: { type: 'language', required: true },
                dir: { type: 'enum', values: DIRECTIONS, nullable: true, default: null },
            },
            html: ['span', { lang: { attr: 'lang' }, dir: { attr: 'dir' } }, 0],
            parse: [{ tag: 'span[lang]', attrs: { lang: { from: 'lang' }, dir: { from: 'dir' } } }],
            inclusive: false,
        },
    },
    formats: { html: 'lossless', text: 'lossy', markdown: 'lossy' },
});
```

`parse` on a node or mark takes data. `parseRules` takes a function for input the data forms cannot match, such as `text-decoration: underline line-through`, which no single style rule reads.

Source: `src/plugins/Strikethrough/feature.ts`

```ts
parseRules: [
    {
        tag: 'span[style*="text-decoration"]',
        mark: 'strike',
        value: (element) => {

                return {};
            }

            return null;
        },
    },
],
```

## The editor part: `defineEditorPart`

`defineEditorPart` comes from `@frontify/fondue-rich-text-editor/authoring`. It takes a feature, or a factory, and the parts of its editor side. `parts` may also be a function of the feature's resolved options.

`defineEditor` takes one plugin per feature of its model in `plugins`. A plugin holds a feature, its editor part and its reader overrides. Each shipped feature has one, such as `boldPlugin`. `modelOf` compiles the model from the same list, so the model and the plugins cannot differ. `defineEditor` throws `definition.missing-plugin`, `definition.orphan-behavior`, `definition.duplicate-id` or `definition.version-mismatch` when the plugins do not cover the model exactly: one plugin per feature, of the same ID and version.

```tsx
import { boldPlugin, corePlugin, defineEditor, linkPlugin, modelOf } from '@frontify/fondue-rich-text-editor';

const plugins = [corePlugin(), boldPlugin(), linkPlugin()] as const;
const model = modelOf(plugins, { id: 'acme.notes', version: 1 });
const definition = defineEditor({ id: 'acme.notes', model, plugins });
```

A host plugin for a feature comes from `definePlugin` for a feature of the host, or from `extendPlugin` for a shipped one: `extendPlugin(plugin, parts)` puts `parts` over the plugin's editor part, and the list you give, such as `toolbar`, replaces the plugin's list whole.

An editor part acts only through `EditorApi`, which its commands, key handlers, suggestion lists and file intake receive. It never touches ProseMirror types.

The API has facets, the members that are objects of functions: `marks`, `blocks`, `attributes`, `insert`, `lists`, `content`, `commands`, `history`, `targets`, `uploads`, `nodeState`, `services`, `overlays` and `panels`. A part names the facets its functions read in `needs`, and the API its functions receive holds those facets and the plain members, such as `selection()` and `select`. A facet missing from `needs` is a type error, and in development it throws an error that names the feature and the facet. Pass `needs` first in the part, and annotate `options` as `JsonObject` when `parts` is a function, so the facets reach the functions below it. Overlay and panel components read the whole API with `useEditorApi`.

### Commands, keys, input rules and toolbar entries

A command is `run(api, payload)`. One call is one undo step. `active` and `enabled` answer queries, so the toolbar shows state. A key names a command or a handler. An input rule is data. A toolbar entry names its command, its label and its icon. A part inside this package gives a `labelKey`, one of the package strings. A host part cannot add to those, so its entry gives `label`: its translations by language tag, which must include `en-US`. An entry with `node`, such as `node: 'asset_image'`, is a command of that node's chrome: it gets no toolbar item, and the More menu, the bubble toolbar's More menu and the context menu offer it only while such a node is selected or holds the caret.

`toggleMark` gives the parts of a mark that toggles, for `defineEditorPart`: it installs `mark.<mark>.toggle`, binds `keys` to it, turns each `inputRules` pair into a `mark-delimiter` rule and adds one toggle entry. The `Strike plugin` story mounts this part with `marks.strike`.

Source: `src/plugins/Strikethrough/editor.ts`

```ts
export const strikeEditor = defineEditorPart(
    strikethrough,
    toggleMark({
        mark: 'strike',
        keys: ['Mod-Shift-x'],
        inputRules: [{ id: 'strike.tildes', open: '~~', close: '~~' }],
        toolbar: { labelKey: 'RichTextEditor_strike', icon: 'IconTextFormatStrikethrough', group: 'marks' },
    }),
);
```

A host entry gives `label` in place of `labelKey`:

Source: `src/docs/authoring/strong.ts`

```ts
label: { 'en-US': 'Strong' },
```

### Commands with a payload

A command declares its payload as data. The package derives the payload's type and checks every call against it. `refuses` rejects a call that the authoring policy forbids, before applicability, and keeps that payload out of the toolbar.

Source: `src/plugins/Heading/editor.ts`

```ts
'heading.set': {
    payload: { fields: { level: { type: 'integer', min: 1, max: 6 } } },
    run: (api, { level }: { level: number }) => api.blocks.set('heading', { level }),
    active: (api, { level }) => api.blocks.active('heading', { level }),
    // A level the policy does not offer is refused before applicability, even in a heading of that level.
    refuses: (policy, { level }) => !policy.creatableHeadingLevels.some((offered) => offered === level),
},
```

### Opening an overlay

`api.overlays.open` opens a component next to the selection, or next to another anchor, such as a link. A command opens a dialog or popover this way, and the toolbar entry sets `opensOverlay: true`.

Source: `src/plugins/Mention/editor.ts`

```ts
'mention.search.open': {
    // The selection's start sits in text that is not code.
    enabled: (api) => {
        const { blockType, verbatim } = api.selection();

        return blockType !== null && !verbatim;

    run: (api) => {
        api.overlays.open(MentionSearchDialog, { resourceTypes }, 'selection');
```

### Decorations

A decoration source draws classes over the text of the blocks of the nodes it names. `derive` returns the ranges of one block, or a promise of them while what it reads still loads. The editor derives again only for a block that a change touched.

Source: `src/plugins/CodeBlock/editor.ts`

```ts
decorations: [
    {
        id: 'code-syntax',
        nodes: ['code_block'],
        derive: ({ attrs, text }) => {
            const { languageId } = attrs;
            if (typeof languageId !== 'string') {
                return [];
            }

            if (highlighter === undefined) {
                return loadHighlighter().then((loaded) => tokensOf(loaded, languageId, text));
            }

            return tokensOf(highlighter, languageId, text);
        },
    },
],
```

### Suggestion lists

A suggestion list opens when the author types its `trigger` at the start of a word. `rules` say how long the query may be. `search` returns options, a page at a time, and the list runs `command` with the chosen option's payload.

Source: `src/plugins/Mention/editor.ts`

```ts
suggestions: [
    {
        trigger: options.trigger as string,
        labelKey: 'RichTextEditor_mentionSuggestions',
        // Names hold spaces, and a mention often follows an opening bracket or quote.
        rules: { afterPunctuation: true, maxQuery: 50, spaces: true, leadingLetters: 0 },
        available: (api) => api.services.references() !== undefined,
        search: async (query, { api, signal, cursor }) => {
            const service = api.services.references();
            if (service === undefined) {
                throw new Error('The host gives no reference search.');
            }

            const page = await service.search(query, resourceTypes, signal, cursor);

            return { items: page.items.map(resultOf), nextCursor: page.nextCursor };
        },
        command: 'reference.insert',
    },
],
```

This part is a function of the feature's resolved options, so it reads the `trigger` option, which the vocabulary part declares.

With `emptyBlock: true` in `rules`, the list opens only at the start of an empty paragraph and closes, keeping the text, when a query with a space finds no option. An option's `group` names the heading it shows under.

### A host block with a node view

A host declares its own block, its node view and its editor part in one file, `callout.tsx`, and joins them with `definePlugin`. The file imports `defineFeature` from `@frontify/fondue-rich-text-editor/model` and the rest from `@frontify/fondue-rich-text-editor/authoring`, as a host does. No server reads the callout, so one file is enough. The `Custom block with a node view` story mounts this example: the Callout button wraps the selection, and the button in the chrome switches the tone through `update`.

Source: `src/docs/authoring/callout.tsx`

```tsx
/** A host block: a box of paragraphs with a tone, stored as `callout`. */
const callout = defineFeature({
    id: 'acme.callout',
    version: 1,
    requires: [{ id: 'core', version: 1 }],
    nodes: {
        callout: {
            group: 'block',
            content: 'paragraph+',
            attrs: {
                tone: { type: 'enum', values: ['note', 'warning'], default: 'note' },
            },
            html: ['aside', { 'data-tone': { attr: 'tone' } }, 0],
            parse: [{ tag: 'aside[data-tone]', attrs: { tone: { from: 'data-tone' } } }],
        },
    },
    formats: { html: 'lossless', text: 'lossy', markdown: 'lossy' },
});

/** The callout's chrome: its tone, a button that switches it, and the editable paragraphs. */
const CalloutView = () => {
    const { attrs, update } = useRichTextNodeView();
    let tone = 'Note';
    let next = 'warning';
    if (attrs.tone === 'warning') {
        tone = 'Warning';
        next = 'note';
    }

    return (
        <>
            <div contentEditable={false}>
                <NodeChromeToolbar aria-label={`${tone} callout`}>
                    <NodeChromeButton label={`Switch to ${next}`} onClick={() => update({ tone: next })} />
                </NodeChromeToolbar>
                <strong>{tone}</strong>
            </div>
            <NodeViewContent />
        </>
    );
};

const calloutView: NodeViewDeclaration = { node: 'callout', component: CalloutView };

/** The host block as one plugin: no server reads its content, so the vocabulary and the editor part share this file. */
export const calloutPlugin = definePlugin({
    feature: callout,
    editor: defineEditorPart(callout, {
        // The commands below read only `blocks`, so only that facet is declared.
        needs: ['blocks'],
        commands: {
            'callout.toggle': {
                run: (api) => api.blocks.wrap('callout'),
                active: (api) => api.blocks.active('callout'),
            },
        },
        toolbar: [
            {
                id: 'callout',
                kind: 'toggle',
                command: 'callout.toggle',
                label: { 'en-US': 'Callout' },
                icon: 'IconInfo',
            },
        ],
        views: [calloutView],
    }),
});
```

The editor part declares `needs: ['blocks']`, the one facet its commands read. A command that reads a facet it did not declare is a type error and, in development, a runtime error that names the feature.

A model that installs a host feature lists its plugin in `plugins`:

```tsx
const plugins = [corePlugin(), calloutPlugin()] as const;
const model = modelOf(plugins, { id: 'acme.notes', version: 1 });
const definition = defineEditor({ id: 'acme.notes', model, plugins });
```

## The reader part: `defineReaderFeature`

`defineReaderFeature` comes from `@frontify/fondue-rich-text-editor/authoring`. It attaches a component to a node or mark that the feature declares. The reader calls it as a function, so pass a function component, not a `memo` or `forwardRef` object. A component that throws renders as a labelled fallback, reports `reader.override-failed` and does not stop the rest of the document.

Source: `src/plugins/Mention/reader.tsx`

```tsx
const Mention = ({ attrs, context }: ReaderNodeProps) => {
    const shown = mentionLabel(attrs, context);
    const note = unavailableNote(shown, context.t);

    return (
        <span data-mention="">
            @<bdi>{shown.label}</bdi>
            {note !== '' && note}
        </span>
    );
};

/** Renders each `mention` node; attach it with `defineReaderFeature`. */
export const mentionReader: ReaderRenderers = { mention: Mention };
```

`defineReaderFeature(feature, renderers)` returns the feature with the renderers attached. Compile that returned feature: the one you passed in carries none. A folder that has a `reader.tsx` also passes the same renderers as `reader` to `definePlugin`, so the reading views of the editor use the same components.

```tsx
import { defineReaderFeature } from '@frontify/fondue-rich-text-editor/authoring';

const model = compileContentModel([core(), defineReaderFeature(mention(), mentionReader)], {
    id: 'acme.notes',
    version: 1,
});
```

## Checking a feature

`runFeatureContract` comes from `@frontify/fondue-rich-text-editor/testing`. It registers the contract cases through the global `describe`, `it` and `expect` of your test runner: the vocabulary, the schema, the commands and toolbar labels, and the codecs and the reader over each stored document you pass in `fixtures`. It needs `axe-core` installed and a DOM test environment, such as happy-dom or jsdom. Pass fixtures. A feature with no fixtures checks no stored content.

```ts
import { runFeatureContract } from '@frontify/fondue-rich-text-editor/testing';

runFeatureContract([core(), myFeature()], { fixtures: [storedDocument], plugins: [myFeatureEditor] });
```
